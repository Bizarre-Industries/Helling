# Helling v0.2 Plan

Status: **implementation in progress**. Bridge plan for Platform Core after
`v0.1.0-alpha`.

## What This Is

v0.2 is a bridge release. It closes the v0.1-beta prerequisites needed by the
platform layer, then ships the first usable Helling-owned control-plane
surfaces: scheduled Incus backups, HMAC webhooks, host firewall rules,
non-admin Incus project restriction, journal-backed audit reads, replayable
events, embedded API docs, and real dashboard pages for schedules, webhooks,
firewall, and audit.

Out of scope: SPICE console, app template gallery, full WebUI audit phases 4-6,
BMC, notifications, Kubernetes, and v0.3+ warning/metrics work.

## Why

**Bridge sequencing.** v0.2 depends on v0.1-beta hardening decisions that were
accepted but not wired end to end: the non-root daemon model, the narrow
systemd helper, Incus loopback mTLS, and encrypted-at-rest control-plane
secrets. Shipping platform CRUD without those prerequisites would create the
wrong host security boundary.

**API-first expansion.** The WebUI and CLI already expose placeholders for
schedules, webhooks, firewall, audit, events, and user scope management. The
OpenAPI contract is the source of truth, so v0.2 expands `api/openapi.yaml`
first and regenerates the Go and TypeScript clients before implementation.

**Operator-visible primitives.** The release should leave operators with
inspectable systemd timers, nftables rules marked with Helling comments,
journald audit entries, signed webhook deliveries, and dashboard pages backed
by real API calls rather than mocks.

## Hard Decisions

- Schedule updates use `PATCH /api/v1/schedules/{id}` for partial mutation.
- Webhook updates use `PATCH /api/v1/webhooks/{id}` for partial mutation.
- Public schedule DTOs use `on_calendar` for systemd `OnCalendar`.
  `cron_expr` is removed from public API and migrated internally.
- v0.2 host firewall scope remains `/api/v1/firewall/host`; groups, ipsets,
  macros, and future rule ordering APIs stay out of scope.
- Events use `GET /api/v1/events` for both SSE streaming and JSON snapshot
  mode. Clients request snapshots with JSON `Accept` headers or a `limit`.
- Incus lifecycle mirroring uses the Incus `/1.0/events` WebSocket.
- `hellingd` is not added to `incus-admin`. Trust registration and revocation
  use a narrow privileged helper surface.
- Webhook secrets are encrypted with age per ADR-039 and never returned by
  list/get responses.
- API docs are embedded in the dashboard with bundled Scalar React. No CDN.
- Scalar is lazy-loaded on the API docs route. Its route chunk is intentionally
  outside the normal data-page bundle budget for v0.2 because the docs viewer
  is an operator reference surface, not part of the repeated dashboard loop.

## ADRs To Amend

- ADR-017: schedule staging directory is `root:helling 0770`; helper commands
  are exactly `install <unit>` and `remove <unit>` for
  `helling-schedule-<uuid>.service|timer`.
- ADR-024: delegated Incus proxying is enforced by per-user restricted
  certificates and project limits, with trust mutation through a helper.
- ADR-036: loopback HTTPS mTLS is the non-admin proxy transport.
- ADR-050: non-root daemon remains the default; `incus-admin` stays outside
  `hellingd`.

## Execution Order

1. Update docs and ADRs. Exit when the accepted v0.2 API/security decisions are
   written and stale plan text is gone.
2. Expand OpenAPI and regenerate clients. Exit when `make generate` and
   `make check-generated` agree.
3. Repair SQL tooling and persistence. Exit when migrations apply in tests and
   `task check:sql` points at the actual store migration path.
4. Implement backend services: events, audit, schedules, webhooks, firewall,
   and Incus project scope. Exit when focused Go tests cover validation and
   persistence.
5. Implement CLI and WebUI surfaces. Exit when frontend tests/build and CLI
   command tests exercise the new routes.
6. Run release gates. Exit when `task check`, `make security-fast`, focused VM
   smoke, and required council review are complete or blockers are documented.

## Acceptance Criteria

- Schedule creation writes validated
  `helling-schedule-<uuid>.service|timer` units, invokes the helper, persists
  metadata, and emits audit/event records.
- Manual schedule run goes through the Helling API and Incus proxy.
- Webhooks sign raw JSON bodies as
  `X-Helling-Signature: sha256=<hex>`, retry at 1s/10s/60s, and retain the
  last 100 deliveries per webhook.
- Webhook URL validation rejects non-HTTPS, localhost, loopback, link-local,
  multicast, private ranges, blocked redirects, and oversized responses.
- Host firewall rules are structured DTOs, render nft invocations as argv,
  persist metadata, and mark nft rules with `comment "helling:<uuid>"`.
- Non-admin Incus proxy requests use per-user restricted project certificates.
- Incus lifecycle events appear as Helling SSE events and webhook deliveries.
- `/api/v1/audit` and `/api/v1/audit/export` read bounded journald output.
- Dashboard schedules, webhooks, firewall, audit, and API docs pages render from
  real APIs.

## Test Plan

- Unit tests: OpenAPI handler validation, schedule unit rendering/helper
  validation, webhook HMAC/retry/SSRF blocking, nft rule rendering/parser,
  audit journal parsing, Incus event mapping, and cert scope enforcement.
- Fuzz/security tests: helper basename validation, firewall DTO validation,
  webhook URL/IP resolution, and event JSON decoding.
- Integration smoke on the Parallels VM:
  - `helling schedule create` writes/enables timer and creates an Incus backup.
  - Incus lifecycle event produces Helling SSE event and valid webhook HMAC.
  - Host firewall rule blocks traffic and appears in `nft list ruleset`.
  - Non-admin user is restricted to assigned Incus project over mTLS.
  - API docs render in the dashboard.
- Final commands: `make generate`, `make check-generated`, `task check`,
  `make security-fast`, focused VM smoke, then council review.

## Council Triggers

This plan touches `api/openapi.yaml`, auth/proxy boundaries, new dependencies,
privileged helper behavior, and firewall behavior. It requires the full council
review path before merge.

## Open Questions For v0.3

- Should webhook delivery support per-event fanout throttles or only global
  daemon concurrency limits?
- Should host firewall rule ordering remain append-only or get an explicit
  reorder endpoint after v0.2?
- Should API docs expose only `/api/v1` public Helling routes or include proxy
  route documentation?

## Don't

- Do not add `hellingd` to `incus-admin`.
- Do not shell-concatenate nft or systemctl commands.
- Do not return webhook secrets from list/get responses.
- Do not reintroduce `cron_expr` in public API.
- Do not implement future firewall groups, ipsets, macros, or reorder APIs in
  v0.2.
